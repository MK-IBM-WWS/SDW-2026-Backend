# Лабораторная работа №2 — база данных облачных тарифов

Серверное приложение на Go, Gin, PostgreSQL и GORM. Оно продолжает первую лабораторную работу: три HTML-страницы сохранены, но тарифы и лайки теперь читаются из PostgreSQL.

## Что выполнено по заданию

- PostgreSQL и Adminer запускаются через `docker-compose.yml`.
- Созданы три предметные таблицы: `users`, `cloud_tariffs`, `user_tariff_likes`.
- Связь пользователей и лайков — многие-ко-многим через таблицу `user_tariff_likes`.
- У всех внешних ключей применяется `ON UPDATE RESTRICT ON DELETE RESTRICT`; каскадного удаления нет.
- Статус тарифа принимает только `черновик`, `опубликован` или `удален`.
- Частичный уникальный индекс не допускает больше одного черновика на одного пользователя.
- Дата создания сохраняется в `created_at`, дата формирования при публикации — в `formed_at`.
- Получение, фильтрация, поиск по ID, создание черновика и публикация выполнены через GORM.
- Логическое удаление выполнено параметризованным SQL-запросом `UPDATE` через `database/sql`, без ORM.
- Удалённые тарифы не выдаются ни плиткой, ни лентой, в том числе по прямому ID.
- Лайки только читаются из БД и отображаются; ставить лайки нельзя.
- Ровно шесть HTTP-маршрутов: три GET и три POST.
- Начальные данные вносятся вручную через Adminer файлом `database/seed.sql`.

Во второй лабораторной авторизации ещё нет, поэтому в обработчиках временно используется пользователь с `user_id = 1`, как в примере методички. Готовый черновик в начальных данных принадлежит пользователю 2. Поэтому у пользователя 1 сначала открывается форма создания; после нажатия «Далее» она становится формой публикации.

## Структура базы данных

### `users` — пользователи

| Поле | Назначение |
| --- | --- |
| `user_id` | Первичный ключ пользователя. |
| `login` | Уникальный логин. |
| `password_hash` | Учебное поле пароля. В реальном проекте здесь должен храниться криптографический хеш. |
| `is_moderator` | Признак модератора. |
| `created_at` | Дата создания пользователя. |

### `cloud_tariffs` — услуги облачного хостинга

| Поле | Назначение |
| --- | --- |
| `tariff_id` | Первичный ключ тарифа. |
| `tariff_name` | Наименование услуги. |
| `short_description` | Краткое описание. |
| `tariff_status` | `черновик`, `опубликован` или `удален`. |
| `image_url` | Прямой URL изображения в MinIO. |
| `video_url` | Прямой URL видео в MinIO. |
| `price_per_month` | Предметное поле: цена в рублях за месяц. |
| `ram_gb` | Предметное поле: объём оперативной памяти в GB. |
| `created_at` | Дата и время создания. |
| `creator_id` | Внешний ключ на `users.user_id`. |
| `formed_at` | Дата и время формирования/публикации; у черновика `NULL`. |

### `user_tariff_likes` — лайки, связь M:N

| Поле | Назначение |
| --- | --- |
| `like_id` | Первичный ключ лайка. |
| `user_id` | Внешний ключ на пользователя. |
| `tariff_id` | Внешний ключ на тариф. |
| `created_at` | Дата установки лайка. |

Составной уникальный индекс по `user_id` и `tariff_id` запрещает пользователю поставить одной услуге несколько лайков.

## Шесть HTTP-маршрутов

| Метод | URL | Технология | Назначение |
| --- | --- | --- | --- |
| GET | `/tariffs?priceLimit=1000` | GORM | Плитка опубликованных тарифов и фильтрация по цене. Допустимы `1000`, `10000`, `500000`. |
| GET | `/tariffs/feed?id=1` | GORM | Просмотр опубликованного тарифа по ID. Параметр `next=true` открывает следующий. |
| GET | `/tariffs/draft` | GORM | Страница создания или заполнения черновика текущего пользователя. |
| POST | `/tariffs/draft` | GORM `Create` | Создание черновика после кнопки «Далее». |
| POST | `/tariffs/publish` | GORM `Updates` | Заполнение описания, цены, RAM и смена статуса на `опубликован`. |
| POST | `/tariffs/delete` | `database/sql` | Логическое удаление запросом `UPDATE cloud_tariffs SET tariff_status = 'удален'`. |

## Подробный запуск на Fedora Linux

### 1. Распаковать проект и открыть терминал в его корне

```bash
unzip cloud-tariffs-app-lab2.zip
cd cloud-tariffs-app
```

Все команды ниже нужно выполнять из каталога, где находятся `go.mod` и `docker-compose.yml`.

### 2. Проверить Go и Docker

```bash
go version
docker --version
docker compose version
```

Если обычный пользователь не имеет доступа к Docker, на Fedora чаще всего используется rootless Podman. Но если Docker уже настроен и команда `docker ps` работает, ничего менять не нужно.

### 3. Запустить PostgreSQL и Adminer

```bash
docker compose up -d
docker compose ps
```

Дождитесь, пока контейнер `cloud-tariffs-postgres` будет иметь состояние `healthy`. Логи при необходимости:

```bash
docker compose logs -f postgres
```

Выход из просмотра логов — `Ctrl+C`; контейнер при этом продолжит работать.

Внешний порт PostgreSQL установлен в `666`, потому что стандартный порт `5432` занят. Запись Compose имеет вид `666:5432`: Go подключается к `localhost:666`, а внутри Docker-сети PostgreSQL продолжает использовать стандартный порт `5432`.

Параметры учебной БД уже записаны в `internal/app/dsn/dsn.go` и совпадают с `docker-compose.yml`, поэтому создавать `.env` и загружать переменные окружения не требуется.

### 4. Загрузить зависимости Go

```bash
go mod tidy
```

Команда добавит недостающие контрольные суммы зависимостей GORM, драйвера PostgreSQL и Viper в `go.sum`.

### 5. Создать таблицы миграцией

```bash
go run ./cmd/migrate
```

Успешный результат заканчивается сообщением:

```text
Миграция выполнена: users, cloud_tariffs, user_tariff_likes
```

Повторный запуск безопасен: `AutoMigrate` не удаляет данные, а индекс создаётся с `IF NOT EXISTS`.

### 6. Подключиться к Adminer

Откройте [http://localhost:8081](http://localhost:8081) и заполните форму:

| Поле Adminer | Значение |
| --- | --- |
| Движок | PostgreSQL |
| Сервер | `postgres` |
| Имя пользователя | `cloud_user` |
| Пароль | `cloud_password` |
| База данных | `cloud_tariffs` |

Важно: в Adminer сервер называется `postgres`, потому что Adminer подключается к соседнему контейнеру по имени сервиса. В `internal/app/dsn/dsn.go` у Go-приложения указан `localhost`, потому что Go запускается на Fedora, вне контейнера.

После входа должны отображаться таблицы `users`, `cloud_tariffs`, `user_tariff_likes`.

### 7. Наполнить БД через Adminer

1. В Adminer нажмите «SQL-запрос».
2. Откройте локальный файл `database/seed.sql` любым редактором.
3. Скопируйте весь SQL в поле Adminer.
4. Нажмите «Выполнить».
5. Через «Выбрать данные» проверьте содержимое всех трёх таблиц.

Начальные записи включают:

- несколько опубликованных тарифов;
- один черновик пользователя 2;
- один удалённый тариф;
- три пользователя;
- реальные строки связи в таблице лайков.

Таким образом, обязательные три состояния услуги присутствуют сразу после заполнения.

### 8. Проверить объекты MinIO

В `database/seed.sql` записаны прямые URL вида:

```text
http://localhost:9000/cloud-tariffs/aws_ec2_medium.jpg
http://localhost:9000/cloud-tariffs/aws_ec2_medium.mp4
```

Используется прежний bucket `cloud-tariffs` из лабораторной №1. Загрузите туда объекты со следующими именами:

```text
aws_ec2_medium.jpg
aws_ec2_medium.mp4
yandex_vm_pro.jpg
yandex_vm_pro.mp4
azure_ai_medium.jpg
azure_ai_medium.mp4
google_ai_max.jpg
google_ai_max.mp4
start.jpg
start.mp4
```

Bucket должен разрешать анонимное чтение. Проверьте любой URL напрямую в браузере. Если MinIO находится на другом адресе, измените `image_url` и `video_url` через Adminer. В отличие от первой лабораторной, URL теперь действительно хранятся в PostgreSQL.

### 9. Запустить веб-приложение

```bash
go run ./cmd/tariffs
```

Откройте:

```text
http://localhost:8080/tariffs
```

Остановка приложения — `Ctrl+C`.

## Проверка всех сценариев

### GET 1 — плитка, фильтр и лайки

1. Откройте `http://localhost:8080/tariffs`.
2. Убедитесь, что видны только опубликованные услуги.
3. Выберите фильтр «До 1 000 ₽».
4. URL должен стать `/tariffs?priceLimit=1000`.
5. Количество лайков должно совпадать с числом строк в `user_tariff_likes` для тарифа.

### GET 2 — лента и ID услуги

1. Нажмите опубликованную карточку.
2. Откроется URL вида `/tariffs/feed?id=1`.
3. Кнопка со стрелкой откроет `/tariffs/feed?id=1&next=true` и сервер выберет следующий опубликованный тариф.
4. Попытка открыть `id=6`, имеющий статус `удален`, вернёт 404.

### GET 3 и POST 1 — создание черновика

1. Откройте `/tariffs/draft`.
2. Пользователь 1 не имеет черновика в начальных данных, поэтому видны только название, URL фото и URL видео.
3. До отправки формы строки в БД нет.
4. Заполните поля и нажмите «Далее».
5. POST `/tariffs/draft` создаст через GORM запись со статусом `черновик`.
6. После перенаправления откроется та же страница с заполненными значениями и кнопкой «Опубликовать».

### POST 2 — публикация

1. Заполните краткое описание, цену и RAM.
2. Нажмите «Опубликовать».
3. POST `/tariffs/publish` через GORM сменит статус на `опубликован` и заполнит `formed_at`.
4. Сервер перенаправит на ленту нового тарифа.

### POST 3 — логическое удаление без ORM

1. Вернитесь в `/tariffs`.
2. Нажмите кнопку корзины на карточке.
3. POST `/tariffs/delete` выполнит сырой SQL `UPDATE` через `database/sql`.
4. Строка останется в таблице, но её статус станет `удален`.
5. Карточка исчезнет, а прямое открытие по ID вернёт 404.

## Где искать ключевые места в коде

| Что показать преподавателю | Файл |

## Остановка и повторный запуск

Остановить контейнеры, сохранив базу:

```bash
docker compose stop
```

Снова запустить:

```bash
docker compose start
```

Удалять volume для обычного перезапуска не нужно. Команда `docker compose down -v` уничтожает все данные PostgreSQL и должна использоваться только тогда, когда вы сознательно хотите создать БД заново.

## Сборка исполняемого файла

```bash
mkdir -p bin
go build -o bin/cloud-tariffs ./cmd/tariffs
./bin/cloud-tariffs
```

Запускать бинарный файл также нужно из корня проекта, поскольку шаблоны, статика и `config/config.toml` подключаются по относительным путям.
