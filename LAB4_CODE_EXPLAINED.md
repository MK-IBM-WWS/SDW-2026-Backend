# Пояснение к коду лабораторной работы 4

В ЛР4 мы заменили учебного постоянного пользователя на настоящего пользователя из JWT, реализовали вход и выход, подключили Redis blacklist и Swagger. В исходниках стоят простые русские комментарии перед действиями и проверками. Возможности сервера не изменены добавлением этих комментариев.

## Как читать Go на этих примерах

- `func` — объявление функции, то есть действия, которое программа может выполнить.
- `type ... struct` — структура: несколько связанных полей, например ID и роль пользователя.
- `type ... interface` — список действий, которые должен уметь выполнять помощник. Например, blacklist должен искать и отзывать токен.
- `:=` — создать переменную и записать в неё результат.
- `err` — ошибка. Если она не равна `nil`, действие не удалось. `nil` здесь означает отсутствие ошибки.
- `if` — проверка условия; `return` — закончить функцию и, если нужно, отдать результат.
- `*Claims` — указатель на структуру Claims. `&body` — адрес структуры body, чтобы функция заполнила её поля.
- `[]byte` — набор байтов; `[]Role` — список ролей; `map` — набор пар «ключ — значение».
- `defer f.Close()` — закрыть файл при выходе из функции, даже если произошла ошибка.
- `context.Context` — сведения о текущей операции, её отмене и ограничении времени. Это не сессия пользователя.
- `*gin.Context` — текущий HTTP-запрос и инструменты для ответа. В нём также можно хранить проверенный ID пользователя.
- `gin.H` — удобная запись словаря для JSON-ответа.
- Метки `json:"login"` задают имя поля в JSON. `json:"-"` запрещает отправлять поле в JSON.
- Метки `gorm:"..."` объясняют ORM, как поле связано с базой данных.

## Регистрация по шагам

1. Клиент вызывает `POST /api/users` с JSON `login` и `password`.
2. `RegisterAPI` читает только допустимые поля. Попытка передать `role`, `user_id` или `is_moderator` будет отклонена.
3. Логин приводится к нижнему регистру, внешние пробелы удаляются. Пароль так не обрабатывается.
4. Проверяются длина и разрешённые символы логина, длина пароля.
5. `bcrypt.GenerateFromPassword` создаёт хеш со случайной солью. Исходный пароль в PostgreSQL не сохраняется.
6. Создаётся пользователь с `IsModerator: false`. Клиент не может назначить себе роль.
7. Репозиторий сохраняет запись. Повторный логин приводит к 409.
8. Ответ 201 содержит пользователя без хеша. JWT регистрация не выдаёт; вход выполняется отдельно.

## Аутентификация по шагам

Аутентификация — проверка личности: действительно ли клиент знает пароль этого аккаунта?

1. `POST /api/users/login` приходит в `LoginAPI`.
2. `strictJSON` читает логин и пароль. `GetUserByLogin` ищет аккаунт в PostgreSQL.
3. `bcrypt.CompareHashAndPassword` проверяет введённый пароль по сохранённому хешу. Пароль не расшифровывается.
4. Если логин или пароль неверен, возвращается один и тот же ответ 401.
5. После успешной проверки `h.Auth.Issue(user)` создаёт токен для найденного пользователя.
6. В claims записываются `user_id`, `role`, `sub`, `iss`, `iat`, `exp`, `jti`. `jti` делает каждый вход отдельным токеном.
7. `SignedString(s.secret)` добавляет подпись HS256. Без серверного секрета нельзя незаметно изменить ID или роль в токене.
8. Клиент получает `access_token`, `token_type`, `expires_in`, `user_id`, `role`. Cookie не устанавливается.

## Проверка JWT и авторизация

В следующих запросах клиент передаёт `Authorization: Bearer <JWT>`. Bearer означает, что для доступа достаточно предъявить действующий токен; его нужно беречь как временный пропуск.

1. Middleware получает заголовок и отделяет слово Bearer от токена.
2. `Validate` проверяет подпись, разрешённый алгоритм HS256, обязательный срок exp, издателя и сведения пользователя.
3. После криптографической проверки выполняется поиск отпечатка токена в Redis. Наличие записи означает отзыв JWT.
4. Проверяется роль: она должна входить в список разрешённых для маршрута.
5. Проверенные ID и роль сохраняются через `c.Set("identity", ...)`. Строка токена и claims сохраняются отдельно для выхода.
6. `c.Next()` запускает основной обработчик, который читает ID через `currentuser.Get(c).ID()`.
7. При создании тарифа этот ID становится `creator_id` автоматически.
8. При публикации и удалении репозиторий сравнивает `CreatorID` тарифа с ID вошедшего пользователя. Чужое изменение возвращает 403.

Проверка личности по JWT и проверка роли/владельца — разные действия. Из правильного JWT не следует разрешение менять любой тариф. Роль зафиксирована в токене на момент входа; изменение `is_moderator` в БД отражается в новом JWT после нового входа.

Для публичных списка и ленты JWT необязателен. С действующим токеном выдача содержит персональные `is_owner` и `is_liked`. С отсутствующим, неверным, истёкшим или отозванным токеном сервер выдаёт данные как гостю. Даже сбой Redis не блокирует это публичное чтение. Защищённый запрос при недоступном Redis получает 503.

## Выход и Redis blacklist

Удалить JWT только у клиента недостаточно: его сохранившаяся копия продолжила бы действовать до exp. Поэтому реализован серверный отзыв.

1. Клиент вызывает `POST /api/users/logout` с тем же Bearer JWT.
2. Middleware проверяет JWT и сохраняет его в контексте запроса.
3. `LogoutAPI` получает claims и исходный токен из контекста.
4. `Service.Logout` вычисляет оставшееся время до exp.
5. `BlacklistKey` получает SHA-256 отпечаток строки JWT и превращает его в имя ключа Redis.
6. `RedisBlacklist.Revoke` выполняет SET: значение `1` с TTL, равным оставшемуся сроку токена.
7. После успешной записи сервер отвечает `logged_out: true`. Клиенту также следует убрать свою копию токена.
8. При следующем защищённом запросе `Exists` обнаружит ключ и проверка закончится с 401.
9. Когда TTL истечёт, Redis автоматически удалит запись. Сам JWT уже будет просрочен и без blacklist.

В Redis здесь нет полноценной сессии пользователя. Он хранит запрет на использование конкретного токена. Выход не отзывает другие JWT того же аккаунта. Публичный список после выхода по-прежнему доступен.

Кнопка Logout внутри окна Authorize в Swagger только убирает токен из интерфейса. Она не заменяет вызов нашего `POST /api/users/logout`.

## Swagger и проверка прав

Swagger UI — браузерный клиент для реальных запросов. Аннотации с `@` описывают пути, параметры, примеры и ответы. `@Security BearerAuth` позволяет UI добавить заголовок Authorization; она сама не защищает сервер.

`RegisterAPI` в `server.go` назначает настоящую защиту через middleware. Поэтому запрос из Postman или другого клиента проходит те же проверки, что запрос из Swagger. Даже если убрать значок замка из Swagger, серверные проверки продолжат работать.

## Термины для защиты

**Cookie, или куки.** Небольшие данные, которые браузер хранит для сайта и отправляет в подходящих запросах. Например, это может быть ID сессии. Cookie — способ хранения и передачи данных; он не равен самой сессии. Наш API получает JWT через заголовок Authorization.

**Сессия.** Состояние взаимодействия пользователя с системой между запросами. В обычной серверной схеме после входа создаётся запись с ID пользователя, а клиент получает случайный ID этой записи, часто в cookie. Сервер по ID находит сессию. Хранить сессии можно в памяти, БД или Redis. При выходе запись удаляется. В нашем проекте выбран JWT и blacklist.

**Redis.** Быстрое хранилище «ключ — значение», которое работает с данными в памяти и может сохранять их на диск. Оно также умеет удалять запись после заданного срока TTL. Redis используют для кэша, сессий и других задач; здесь он хранит отозванные JWT. В Compose включены AOF и постоянный том для сохранения blacklist.

**JWT.** Формат токена с данными пользователя. Наш подписанный JWT состоит из заголовка, данных и подписи. В заголовке указан алгоритм, в данных — ID, роль и срок, подпись подтверждает, что данные не изменили. Содержимое не шифруется. JWT может передаваться разными способами, в том числе в cookie; у нас используется Authorization: Bearer.

**Аутентификация.** Проверка «кто ты?»: логин и пароль подтверждают личность аккаунта, а действующий JWT позволяет узнать его в следующих запросах.

**Авторизация.** Проверка «что тебе разрешено?»: например, вошедшему пользователю нельзя публиковать или удалять чужой тариф.

**Деавторизация.** Выход и прекращение доступа по текущему удостоверению. У нас это отзыв JWT через Redis blacklist и удаление его копии у клиента.

**SSO.** Single Sign-On, единый вход. Пользователь входит у общего поставщика идентификации, а несколько приложений доверяют подтверждению от него. Например, один университетский вход для почты, учебного портала и библиотеки. Это не просто одинаковый пароль на разных сайтах. В ЛР4 SSO не реализован.

**Двухфакторная аутентификация.** Вход с подтверждениями двух разных типов: например, пароль, который человек знает, и одноразовый код с устройства, которым он владеет. Два пароля являются одним типом фактора и сами по себе не дают 2FA. В ЛР4 используется только пароль, без второго фактора.

**RSA.** Криптографический алгоритм с парой ключей: открытым и закрытым. Открытый можно раздавать; закрытый хранится в секрете. В варианте шифрования открытым ключом защищают сообщение для владельца, а закрытым его расшифровывают. В варианте подписи закрытым ключом создают подпись, а открытым её проверяют. Наш JWT использует HS256 с одним общим серверным секретом, а не RSA. Поэтому RSA нужен для понимания теории, но в нашем коде не применяется.

**Хеш и подпись.** Хеш пароля bcrypt позволяет проверить пароль, не сохраняя его исходный текст. SHA-256 отпечаток JWT у нас нужен для ключа Redis. Подпись HS256 нужна для проверки подлинности и неизменности JWT. Это три разных применения криптографии в одной работе.

## Проверка версии с комментариями

Исполняемые токены всех Go-файлов сравнены с исходным архивом без учёта комментариев. Значения `.env`, Docker Compose и зависимостей `go.mod` сохранены. Исходные Swagger-аннотации также сохранены. Запуск выполняется по прежней инструкции; комментарии Go на выполнение программы не влияют.
